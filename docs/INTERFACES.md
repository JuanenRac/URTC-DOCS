# Interfaces

Who owns each contract between the repositories, where it is written down, who uses it and what is checked automatically. A contract here is anything one repository produces and another consumes: a wire format, a file, a naming rule, a command-line entry point.

The rule that runs through the table: **the owner is the repository whose document or code is the reference, not the repository that implements it first.** Where the reference is prose only (the CAN protocol), the implementations are copies of a reading of that prose, and `CAN_PROTOCOL_DUPLICATION.md` says what that costs.

## The contracts

| Contract | Owner and reference | Consumers | What checks it |
|---|---|---|---|
| **CAN application protocol**: identifiers, DLC, payload layouts, big-endian multi-byte fields, magic payloads of destructive commands, telemetry periods | `URTC`: `docs/CANBUS.TXT` (prose; ID headers plus a summary list at the end) | The firmware (`src/F303-master`, `src/F303-slave`), URTC-FLASHER (`flasher_config.py`), URTC-TESTER (`tester_config.py`, `advanced_protocol.py`), URTC-WEB-STUDIO (`src/lib/canIds.ts`, `src/lib/flasher.ts`) | The firmware has host tests for the dispatch routing, the thermal guard, the version wire format and others (`tests/*.c`). Each tool tests its own copy against its own fixtures. **Nothing compares the copies with each other or with the prose.** |
| **CAN bootloader protocol**: enter, start, HMAC chunks, data, page acknowledgement, end, status, heartbeat, downgrade authorisation, read-back | `URTC`: `docs/CANBUS.TXT`, section "CAN BOOTLOADER PROTOCOL" (`0x7F0`-`0x7FF`) | Main-board and slave bootloaders; URTC-FLASHER (`flasher_protocol.py`); URTC-WEB-STUDIO (`src/lib/flasher.ts`) | FLASHER runs the whole sequence against `MockCAN`, a simulated bootloader written from the same prose. Its README states that the simulation is more forgiving than the real bootloader was (two defects hid behind it). The bootloader itself has not run on a board. |
| **Version query and the patch number**: `0x7F8` query, `0x7F9`, `0x7FA`, `0x7E9`, the patch in the high byte of the minor field of `0x7F4`/`0x214`, slave `0x217`/`0x218` | `URTC`: `docs/CANBUS.TXT`, "FIRMWARE PATCH NUMBER" and its host contract | Both bootloaders and the application; URTC-FLASHER 0.2.9 and URTC-WEB-STUDIO 0.2.8 implement the host side | Pure C wire helpers with sanitizer tests (`tests/test_version_wire.c`); `tests/test_patch_number.py` in FLASHER and `versionPatch.test.ts` in WEB-STUDIO against simulators. | **Expansion slave relay**: `0x210`-`0x221` over the I2C link | `URTC`: `docs/CANBUS.TXT` and `docs/EXPANSION.TXT` | Main-board firmware (relay), slave firmware, FLASHER, WEB-STUDIO | No host tool defines `0x220`/`0x221` (generic slave register write/read) at the time of reading. |
| **SLCAN**: ASCII frames over a virtual serial port (`tIIILdd...`, bitrate `Sx`, open `O`, listen-only open `L`), terminated by a carriage return | No repository owns it: it is the Lawicel convention. | **SocketCAN** (Linux) and **python-can** | The kernel and the `python-can` project | FLASHER (both), TESTER (SocketCAN only) | Frame packing was checked against `struct can_frame` in FLASHER; python-can is an optional extra with tests. |
| **Release assets of the firmware**: file names that carry their version, `.sha256` sidecars, `.manifest.json` with `sha256`, `crc32`, `size_bytes`, `hardware_id` and, for application images, `hmac_sha256`, `signing_key_kind`, `signing_key_id`; the index `firmware_manifest.json` | `URTC`: `docs/FIRMWARE_DISTRIBUTION.md`, `tools/publish_release_assets.py` (also in `URTC-SMART-RACK` and `URTC-VISION-TOOL`) | URTC-FLASHER (`flasher_github.py`, `tools/sync_firmware.py`), URTC-WEB-STUDIO (`githubRelease.ts`, `scripts/sync-firmware.mjs`) | `tests/test_publish_release_assets.py` in the firmware repository; the download rules (hosts, sizes, digests) have tests in both tools. |
| **Firmware signing**: HMAC-SHA256 over the whole image, key injected at build time from the file named by `URTC_SIGNING_KEY_FILE`, public development key otherwise | `URTC`: `docs/FIRMWARE_SIGNING.TXT`, `firmware_signing.py` | Both bootloaders; the tools only transport the published signature | FLASHER computes CRC32 and HMAC-SHA256 identically to the C code (verified byte for byte); `tests/test_signing_policy.py` covers the refusal rules. |
| **Project manifest** `urtc.project.json`: `schema_version`, `ecosystem`, `name`, `version`, `role`, `stack`, `technologies`, `deployment_target`, `maturity`, `family`, `parent`, `build`, `notes`, `native_version` | `URTC-UPDATER`: `src/urtc_updater/project_manifest.py` (`parse_manifest`); the same keys are required by every repository's `tools/ci_validate.py` | URTC-UPDATER, the dashboard of the profile repository, URTC-DOCS (the catalogue), every repository's CI | `ci_validate.py` in each repository; the UPDATER's tests; the catalogue check of URTC-DOCS. |
| **Shared CI checks**: `tools/ci_validate.py`, `tools/_doc_policy.py`, `tools/_readme_parity.py`, `bump_manifest_version.py`, `tools/build_test.py` | `HYDRA-UMC-SDK` (the two `_` modules, kept in sync by its sync scripts); the rest is the copy in `URTC` | Every URTC repository | Each repository's CI runs its own copy. The copies are not byte-identical across the ecosystem (see `CAPABILITY_MATRIX.md`). |
| **`build-test` entry point**: `build-test.sh` / `build-test.bat` run `tools/build_test.py`, which never raises a version or edits the changelog | The ecosystem convention (`tools/build_test.py`) | URTC-UPDATER runs it in the staging checkout before promoting an install or an update | `ci_validate.py` requires the three files to exist. |
| **Odometer version scheme**: patch +1, carry into minor and major past 9 (`0.3.9` -> `0.4.0`); four components from `0.8.0` | `bump_version.py` and `bump_manifest_version.py` in each repository | Every manifest, changelog and native version file | `ci_validate.py` requires the native version, the manifest and the newest changelog heading to agree. |
| **Dashboard refresh**: a `repository_dispatch` event `ecosystem_project_updated` sent by each repository's `dashboard-dispatch.yml` after a push to `main` | The profile repository (`build-dashboard.yml`) | All repositories | Optional: with no `ECOSYSTEM_DASHBOARD_DISPATCH_TOKEN` secret the workflow does nothing and succeeds; the dashboard also rebuilds on a schedule. |

URTC-DOCS compares it itself in its tests. |

## Boundaries that are deliberately not contracts

* **URTC-SMART-RACK** and **URTC-VISION-TOOL** have their own frame formats (versioned framing with a CRC8, command validation, a link watchdog or a sensor-frame protocol) implemented in C with host tests. They are *not* the tool-head CAN reference, and no document traced for this repository says how those frames would be carried on the CAN bus.
* **The profile README tables** carry version numbers that a bot synchronises from the manifests. They are not a contract and are never edited by hand.
* **`ELECTRO-HOBBY-3D-UPDATER`** only dispatches to the three ecosystem updaters; it has no manifest in the URTC schema.

## Documents that disagree with the code at the time of reading

* `URTC/docs/FIRMWARE_DISTRIBUTION.md` says that the consumers still have to be changed and that none of them was modified. The changelogs of URTC-FLASHER 0.2.9 and URTC-WEB-STUDIO 0.2.8 say they now read the release assets, so the section "What each consumer must change" describes work that has since been done.
* `URTC/docs/CANBUS.TXT` says in one passage that a host cannot tell "which of the 12 tool profiles" a board is jumpered for; the same document, the manifest and the README define 25 profiles.
* The README of URTC-TESTER says its SLCAN and SocketCAN classes "are identical" to the flasher's. They have diverged (see `CAN_PROTOCOL_DUPLICATION.md`).
